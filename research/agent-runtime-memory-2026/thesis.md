# Thesis

## Central Thesis

Agent Memory 不是一个“选哪种数据库”的问题，而是一套长期状态的权力与生命周期设计：系统必须决定谁能把什么写成记忆、旧事实如何失效、证据如何保留、哪些内容在何时进入上下文。TencentDB、Mem0、Graphiti、Letta 没有给出同一道题的四个实现，而是分别把团队资产治理、紧凑记忆服务、时间化事实图和 Agent 自治状态当成核心。

## Common Misreading

常见理解是把四个项目放在“抽取、存储、向量检索、注入”的统一流水线上比较，然后寻找功能最多或 benchmark 最高的一个。这个理解会遮蔽决定长期可靠性的差异：自动写入能否覆盖过去、冲突是删除还是失效、来源能否追溯、记忆由应用还是 Agent 维护、团队共享是否需要版本和权限。

## Supporting Evidence

1. Mem0 v3 从旧的四操作模型转向单次 LLM 的 ADD-only pipeline，把破坏性修订留给显式 API；说明写入权本身就是设计变量。
2. Graphiti 同时保留 episode、事实有效时间和系统记录时间，矛盾事实失效但不物理删除；说明“记住当前真相”与“保留历史证据”可以同时建模。
3. Letta 当前从 always-visible memory blocks 转向 Git-backed MemFS，由 Agent 用文件工具、commit、worktree 和 dreaming 维护长期状态；说明记忆也可以是 Agent 的可操作工作空间。
4. TencentDB 将 Chat Memory、Skill、Wiki、CodeGraph 统一到 Owner、ACL、版本与 Agent Binding 控制面，同时保留不同读取方式；说明团队记忆的难点不只是召回，更是经验资产的治理和装配。

## Counterargument

应用开发者最终仍需要一个简单 API：写入、搜索、把结果塞进 prompt。把问题提升为“权力与生命周期”可能显得过度设计，而且四套系统完全可以组合使用，并不互斥。

回应是：简单 API 没有消除这些决策，只是把默认值藏起来。自动覆盖、无限追加、时间失效、Agent 自主编辑或管理员审核都会产生不同的错误模式。系统可以组合，但必须先指定每类记忆的权威来源和唯一修改路径，否则会出现多个互相矛盾的真相层。

## Conditions

论点适用于跨会话、跨任务或跨 Agent 的长期状态。对于单轮问答、短生命周期工作流或纯文档检索，完整 Memory 系统可能没有收益。四类方案的选择还取决于数据变化速度、错误容忍度、治理要求、Agent 自主程度和可接受运维成本。

## Unproven

- 四套系统在相同数据、模型与预算下的端到端质量和成本排序。
- Agent 自主管理文件是否长期优于后台自动抽取。
- ADD-only 是否在真实长期使用中比自动覆盖更可靠，还是只把清理成本推迟。
- 团队资产控制面与时间图谱、个性化记忆服务组合后的最优权威边界。
