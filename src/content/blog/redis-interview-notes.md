【第 1 页】Redis 为什么这么快

后端八股 · Redis 篇 01

一句话答案：快 的根本原因是数据全在内存，单线程省掉了锁和切换开销，epoll 又让一个线程扛住了所有连接。

机制展开：第一，纯内存操作。读写都发生在内存里，不碰磁盘——内存随机访问是百纳秒级，SSD 要几十微秒，差两个数量级，这是单机 10w+ QPS 的根基。而且瓶颈因此在内存容量和网络带宽上，不在 CPU——这直接解释了为什么 Redis 不需要多线程去榨 CPU。第二，单线程执行命令。没有锁竞争、没有线程上下文切换、不用考虑并发安全。不这样做，每条命令都要加锁，复杂度暴涨但收益有限。第三，IO 多路复用。内核用 epoll 同时监听所有 socket，哪个连接有数据就处理哪个，一个线程就能服务成千上万个连接，不需要一连接一线程。

追问链：
①「Redis 到底单线程还是多线程？」——命令执行始终单线程，但 Redis 进程不止一个线程：2.6 起就有后台线程处理关闭文件和 AOF 刷盘，4.0 加了 lazyfree 线程异步释放内存，6.0 又把网络 IO 读写做成了多线程。
②「6.0 为什么加多线程？」——网络带宽上来后，读写 socket 和协议解析成了新瓶颈，这部分并行化收益大，又不破坏命令执行的简单性。

加分点：删大 key 用 unlink 别用 del——del 同步释放内存会卡住主线程，unlink 把释放动作丢给 lazyfree 后台线程。

【第 2 页】数据类型与应用场景

后端八股 · Redis 篇 02

一句话答案：五大基本类型按数据形态选，四个扩展类型按业务场景选。

机制展开：String，底层 int 或 SDS，用于缓存 JSON 对象、计数器（incr 原子自增）、分布式锁、共享 Session。Hash，底层压缩列表或哈希表（7.0 起 listpack 替代压缩列表），适合存"属性会频繁变化的对象"，经典场景购物车：用户 id 作 key、商品 id 作 field、数量作 value。List，3.2 起统一 quicklist，两头进出快，做消息队列（lpush + brpop 阻塞消费）。Set，整数集合或哈希表，自动去重：点赞、共同关注（交集）、抽奖（spop）。ZSet，压缩列表或跳表，带分数排序：排行榜（zincrby 加分、zrevrange 取前 N）。扩展类型四件套：BitMap 签到打卡（5000 万用户只要约 6MB）、HyperLogLog 数 UV（固定 12KB，误差 0.81%）、GEO 附近的车、Stream 专业消息队列。

追问链：「List 和 Stream 做消息队列怎么选？」——Stream 补齐了 List 的两个缺陷：自动生成全局唯一消息 ID、支持消费组。但 Redis 做队列天然有两个风险：AOF 异步刷盘可能丢消息、内存有限消息积压会 OOM。数据不敏感、积压少可用，否则上专业 MQ。

加分点：存对象选 String 还是 Hash？整体读写用 String + JSON，频繁改单个字段用 Hash，避免每次改一个属性就重写整个 JSON。

【第 3 页】缓存穿透 · 击穿 · 雪崩

后端八股 · Redis 篇 03

一句话答案：雪崩是一大片缓存同时失效，击穿是单个热点失效，穿透是查压根不存在的数据。

机制展开：雪崩，大量 key 同时过期或 Redis 宕机，请求洪峰全部压到数据库，可能引发连锁崩溃。解法四板斧：过期时间加随机值打散；互斥锁只放一个请求去重建缓存；后台线程异步更新缓存不设过期；再加上熔断限流保命，以及主从集群高可用 + 提前缓存预热。击穿，本质是雪崩的子集——某个热点 key（比如秒杀商品）过期的瞬间，海量并发直接打到库。解法：互斥锁，或热点数据不设过期、由后台异步更新。穿透，查询的数据缓存和数据库都没有，缓存永远建不起来，每次都打到库，常见于恶意请求不存在的 id。解法换了一套：入口校验参数合法性；把空结果也缓存起来设短过期；布隆过滤器——说"不存在"就一定不存在，说"存在"可能误判，正好用来把恶意 key 拦在缓存之前。

追问链：「为什么穿透的解法和另外两个不一样？」——雪崩击穿的数据在数据库里是存在的，缓存恢复压力就降了；穿透的数据压根不存在，必须从入口拦，不然缓存帮不上任何忙。

加分点：一句话口诀——穿透查的是"没有的数据"，击穿倒的是"一个热点"，雪崩倒的是"一大片"。

【第 4 页】数据库和缓存的一致性

后端八股 · Redis 篇 04

一句话答案：主流方案 Cache Aside——读先缓存后数据库，写先更新数据库再删缓存。

机制展开：第一个问题，写操作为什么是"删缓存"而不是"更新缓存"？懒加载思想：写进缓存的数据可能根本没人读，白写；更致命的是并发写时，两个写请求更新缓存的顺序可能颠倒，把旧值写回缓存。删就没有这两个问题，下次读的时候自然会加载最新值。第二个问题，为什么"先更新库再删缓存"而不是反过来？如果先删缓存，删掉的一瞬间来了个并发读，把数据库的旧值查出来写回了缓存，这份旧数据就常驻了；而先库后缓存的不一致，只发生在"缓存恰好失效、且读请求比写请求还慢"这种极小概率场景，窗口短得多。兜底手段：延迟双删（更新完库睡几毫秒再删一次缓存），或订阅 binlog（canal）异步删，删除失败还能靠消息队列重试。

追问链：「能不能做到强一致？」——可以，读写都上分布式锁串行化，但性能代价大，缓存场景一般接受最终一致即可。

加分点：删缓存失败别慌——塞进消息队列重试，或者干脆依赖 binlog 异步删这条兜底链路，天然保证最终一致。

【第 5 页】持久化：RDB 与 AOF

后端八股 · Redis 篇 05

一句话答案：RDB 是定时快照丢得多恢复快，AOF 是记命令丢得少恢复慢，4.0 的混合持久化两头兼顾。

机制展开：RDB 把某一时刻的内存数据整体写成二进制文件。主流触发是 bgsave：fork 一个子进程去写文件，主进程继续服务，父子进程靠写时复制共享内存页，子进程看到的是 fork 那一刻的数据。也可以用 save m n 自动触发（m 秒内至少 n 次修改）。优点是文件紧凑、恢复快；缺点是两次快照之间的数据会丢。AOF 把每条写命令追加进日志。Redis 的特别之处是先执行命令、成功后才记日志——不会记错命令、不阻塞当前写，代价是宕机可能丢最后一条。刷盘三档：always 每条都刷（最多丢 1 条）、everysec 每秒一次（默认，丢 1 秒）、no 交给操作系统。文件膨胀靠 AOF 重写解决：fork 子进程根据当前内存数据反推一份最小等价命令集。混合持久化（4.0+）：重写时先写 RDB 全量、再追加之后的增量命令，恢复快 + 丢得少。

追问链：「生产上怎么配？」——能接受分钟级丢失就纯 RDB；一点不能丢就 AOF everysec；4.0 以后直接混合持久化。

加分点：fork 瞬间主进程是阻塞的（要复制内存页表），而且写时复制在极端情况下主进程把数据全改一遍，内存占用会接近翻倍——大内存实例要留够余量。

【第 6 页】过期删除 vs 内存淘汰

后端八股 · Redis 篇 06

一句话答案：过期删除清的是"已经到期的 key"，内存淘汰是"内存满了挑 key 牺牲可能删没到期的"。

机制展开：过期删除用"惰性 + 定期"组合。惰性删除：访问 key 时顺手检查，过期就删——问题是没人访问的过期 key 一直占内存。所以有定期删除：默认每秒 10 次，每次随机抽 20 个带过期时间的 key，把过期的删掉；如果这一轮过期比例超过 25%，说明过期 key 太多，继续抽，单轮时间上限 25ms 防止卡死线程。内存淘汰是另一件事：运行内存超过 maxmemory 时触发，共 8 种策略。重点记四个——noeviction（默认，不淘汰，写入直接报错）、allkeys-lru（全库淘汰最近最少使用，缓存场景最常用）、volatile-lru（只在设了过期时间的 key 里淘汰）、allkeys-lfu（4.0 新增，淘汰访问频率最低的）。Redis 的 LRU 是近似实现：不维护链表，只在对象头的 24 bit 记最后访问时间，淘汰时随机采样 5 个 key 挑最久没用的——省内存，但治不了缓存污染（偶发批量访问的数据赖着不走）。LFU 专治这个：24 bit 拆成 16 bit 时间 + 8 bit 频次，频次会随时间衰减，新 key 初始频次 5。

追问链：「和 MySQL 的 LRU 有什么区别？」——InnoDB 是严格的 LRU 链表，还分成 new/old 两区，防全表扫描把热点页冲掉。

加分点：缓存污染场景（偶尔被批量扫一遍的冷数据）选 allkeys-lfu 而不是 lru，这是 4.0 加 LFU 的动机。

【第 7 页】主从复制

后端八股 · Redis 篇 07

一句话答案：第一次全量同步靠 RDB，之后靠长连接命令传播，断线重连先尝试增量。

机制展开：第一次同步三阶段。第一阶段：从库执行 replicaof 后发 psync 命令，带上主库 id 和复制进度 offset；主库一看是第一次，回复"全量同步"，并把自己的 id 和 offset 发给从库。第二阶段：主库 bgsave 生成 RDB 发给从库，这期间的新写命令先攒在 replication buffer 里；从库清空自己的数据、载入 RDB。第三阶段：主库把攒着的命令发过去，之后进入命令传播——主库每执行一条写命令就发给从库，长连接持续同步。断线重连时不一定重来全量：从库带着 offset 回来，主库去查 repl_backlog 环形缓冲区，offset 还在里面就只补差值（增量复制）；写流量太大把这段覆盖了，只能重新全量。

追问链：「从库很多时全量同步会怎样？」——主库要给每个从库生成、发送 RDB，压力集中。解法是级联复制：从库再挂从库，分摊主库压力。

加分点：repl_backlog 默认只有 1MB，写流量大的集群适当调大它，能显著减少"被迫全量同步"的次数。

【第 8 页】哨兵 Sentinel

后端八股 · Redis 篇 08

一句话答案：哨兵解决"主库挂了没人自动切换"的问题，靠多数派确认下线、自动选新主。

机制展开：第一步判断下线分两轮。主观下线：一个哨兵 ping 主库，超过 down-after-milliseconds 还不通——但可能只是这个哨兵自己网络抖，做不了数。客观下线：询问其他哨兵，认为下线的数量达到 quorum 个才算真的挂，多数派排除了个体误判。第二步选执行者：哨兵之间先选出一个 leader 来执行故障转移（Raft 思路：每个哨兵每个任期只有一票，先到先得，拿到超过半数选票的当 leader）。第三步选新主库，规则依次比较：优先级（replica-priority）谁大谁上；一样就比较复制偏移量，谁数据更全谁上；还一样就比 runid，谁小谁上。最后通知客户端："主库换人了，改连这个地址"。

追问链：「哨兵为什么至少部署 3 个？」——部署 2 个的话，其中一个挂了就凑不齐多数派，客观下线和 leader 选举都做不下去；3 个才能容忍 1 个故障。

加分点：客户端不是直接连哨兵拿地址，而是订阅哨兵的 +switch-master 频道被动感知切换——面试说出来这句，说明你真用过。

【第 9 页】分片集群 Cluster

后端八股 · Redis 篇 09

一句话答案：单机扛不住内存和写流量时，把 16384 个哈希槽拆到多个主节点，key 按槽定位。

机制展开：为什么要集群——单机内存有上限、写性能到顶、网卡流量打满，都要靠水平拆分解决。做法：全集群共 16384 个哈希槽，分配到多个主节点；每个 key 用 CRC16 计算 hash 值再对 16384 取模，落在哪个槽就归哪个节点管。每个主节点再挂从节点防单点，主挂了从自动顶上（这里不需要哨兵，集群节点自带选举）。客户端可以连任意节点：key 不在这个节点，返回 moved 错误带上正确地址，客户端会缓存这张槽位表，之后直连；槽正在迁移时返回 ask 临时重定向，不更新缓存。节点之间用 gossip 协议互相 PING/PONG，传播集群状态。

追问链：「为什么是 16384 个槽？」——CRC16 产出 16 位，本来可以 65536 个。作者 antirez 的理由：节点心跳包里要带一份槽位表 bitmap，16384 个槽只要 2KB，65536 要 8KB；而且集群设计规模上限约 1000 节点，16384 完全够分。

加分点：集群下 mset 这类多 key 命令要求所有 key 在同一个槽，生产上用 hash tag——把 key 写成 user:{1000}:cart 这种形式，大括号内容相同就哈希到同一个槽。

【第 10 页】分布式锁

后端八股 · Redis 篇 10

一句话答案：一条原子命令加锁、唯一值 + Lua 脚本解锁、看门狗续期，这三步演进是完整答案。

机制展开：第一版 setnx + expire 两条命令，中间宕机就出现死锁——锁永远不过期。第二版合成一条：set key 唯一值 nx px 过期时间，加锁原子了。新问题：业务没执行完锁先过期了，A 释放的其实是 B 的锁——所以 value 要放每个客户端的唯一随机值，解锁用 Lua 脚本"先 get 校验是自己的值，再 del"，两步原子执行。还有一个坑：业务超时锁过期，别人进来并发了——看门狗机制定时给锁续期（Redisson 默认每过锁有效期的三分之一就续一次），业务做完才停止续期。主从架构的终极问题：主库写入锁成功还没同步给从库就挂了，从库顶上来没有这把锁，两个客户端同时持锁——Redlock 向多个独立的 Redis 主节点加锁、多数成功才算持有，但 Martin Kleppmann 和 antirez 为它的安全性激烈争论过（GC 停顿、时钟跳变都可能破坏它），生产上更常见的是单实例 + 看门狗，或者直接换 etcd/zookeeper。

追问链：「Redis 锁和 zk 锁怎么选？」——Redis 性能高、实现轻，但可靠性是 AP 系统的妥协；zk 临时节点 + 版本控制更可靠，代价是性能低、运维重。

加分点：锁的过期时间不要写死拍脑袋——用看门狗的"无固定过期 + 自动续期"模式，比 magic number 靠谱得多。
